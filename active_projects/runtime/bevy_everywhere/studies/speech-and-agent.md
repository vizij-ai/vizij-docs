## Findings

1. **`@vizij/speech-react` has exactly one consumer: the standalone.** The package (0.1.2) exports `useSpeechRecognition`, `useConversation`, `useSpeechPlayback`, the Polly client `fetchVisemeData`, the Deepgram/OpenAI key helpers, the viseme map and pose-path helpers (vizij-web/packages/@vizij/speech-react/src/index.ts:1-54). The only import in the monorepo is vizij-web/apps/vizij-standalone/src/hooks/useSpeechController.ts:5-15; the only `package.json` depending on it is the standalone's.
2. **vizij-authoring and vizij-showcase carry their own copies of the same code and do not use the package.** `visemeMapping.ts`, `pollyVoices.ts`, `types/polly.ts` are byte-identical between `apps/vizij-authoring/src` and the package; `useConversation.ts` differs by 2 lines, `pollyApi.ts` by 3, `useSpeechRecognition.ts` by 45, `useSpeechPlayback.ts` by 180 (authoring's is the larger, with its own `createVisemeTimeline.test.ts`). The showcase's `services/pollyApi.ts` differs by 3 lines and its `VoicePanel.tsx` reimplements the playback cursor. The package declares `@vizij/render` as a dependency (package.json:33) but nothing in its `src/` imports it.
3. **STT is Deepgram over a browser WebSocket, keyed in the page.** `useSpeechRecognition` captures `getUserMedia` audio with `MediaRecorder` (`audio/webm`, 250 ms chunks) and streams it to Deepgram `nova-3` with `vad_events`; `SpeechStarted`/`UtteranceEnd` drive `userSpeaking` and the auto-stop (src/hooks/useSpeechRecognition.ts:157-225). The API key travels as `Authorization: Token …` from the page (177).
4. **The LLM turn is OpenAI Chat Completions called directly from the browser**, default `gpt-4o-mini`, bearer key in the request (src/hooks/useConversation.ts:22, 60-68).
5. **TTS is the Vizij cloud function (AWS Polly behind it), and the web plays it through an `<audio>` element.** `fetchVisemeData` POSTs `{voice, text}` to `${apiBase}/tts/get-visemes` and `/tts/get-audio` (src/services/pollyApi.ts:12-43). `useSpeechPlayback` sets the blob as `audio.src`, and a `requestAnimationFrame` loop reads `audio.currentTime` to fire viseme transitions (src/hooks/useSpeechPlayback.ts:317-330). The audio element's clock is the viseme clock.
6. **The web lipsync writes pose weights directly, in a vocabulary that is not the face standard's.** Paths are `rig/<faceId>/poses/<poseId>.weight` (useSpeechPlayback.ts:154-163, POSE_WEIGHT_INPUT_PATH_PREFIX in src/lib/poseUtils.ts:3), animated with `animateValue`/`setInput` and a 45-320 ms ramp (191-224). Polly codes map to the face's pose ids `p t t_2 s f k i r u a e e_2 o o_2 pose_pzzzfnvy` (src/lib/visemeMapping.ts:1-17, 64-83), not to the standard's 15 shapes.
7. **Keys resolve CLI → env → localStorage.** Browser side: `VITE_DEEPGRAM_API_KEY` / `VITE_OPENAI_API_KEY`, then `localStorage` keys `vizij_deepgram_api_key` / `vizij_openai_api_key` (src/services/deepgramConfig.ts:1-18, openaiConfig.ts:1-18). The standalone's Tauri host resolves `--deepgram-key`/`--openai-key`/`--api-url`/`--auto-mic`/`--speech-mode`/`--silence-ms` then env `DEEPGRAM_KEY`|`VITE_DEEPGRAM_API_KEY`, `OPENAI_KEY`|`VITE_OPENAI_API_KEY`, `API_URL`|`VITE_API_URL`, `AUTO_MIC`, `SPEECH_MODE`, `SILENCE_MS` (apps/vizij-standalone/src-tauri/src/lib.rs:196-229, 1510-1537) and hands them to the webview over `get_speech_keys` (1323-1343); the webview persists CLI keys into localStorage (useSpeechController.ts:122-149).
8. **The standalone's speech controller composes the three hooks into `echo` and `conversation` modes.** Mode = CLI/env > `speechConfig.mode` > `"echo"` (useSpeechController.ts:196). Echo sends the final transcript to TTS; conversation sends it to OpenAI, parses an optional `{text, emotion}` JSON reply, activates the emotion, then speaks (309-345).
9. **`speechConfig` is bundle metadata, typed in `@vizij/render`.** `VizijSpeechConfig` = `voice, mode, agentName, systemPrompt, speakingInputPath, userSpeakingInputPath, thinkingInputPath, visemeGroupId, emotionGroupId, apiBaseUrl, autoActivateMic` (vizij-web/packages/@vizij/render/src/types/vizij-bundle.ts:100-123), read from `bundle.metadata.speechConfig` (apps/vizij-standalone/src/App.tsx:342-347). Speech is enabled only when it is present (useSpeechController.ts:190).
10. **The state topics and the emotion group are face-graph inputs under `rig/<faceId>/speech/…`, outside the face standard.** Speaking (`/speech/speaking`) is written 1 on audio play and 0 on stop (useSpeechPlayback.ts:289-297, 444-452); user speaking follows Deepgram VAD (useSpeechController.ts:369-382); thinking = conversation mode and (LLM in flight or TTS preparing) (272-274, 384-397). The emotion group's pose ids are offered to the LLM (226-230) and activated as `rig/<faceId>/speech/emotion/<name>` 0/1 (277-294). The viseme group is `speechConfig.visemeGroupId`, else the first pose group whose path or name contains "viseme" (259-264; useSpeechPlayback.ts:122-132). None of these paths appears in docs/face-standard.md (vizij-rs/docs/face-standard.md:31-129).
11. **The standalone's `speak`/`interrupt`/`mute_microphone` are WS-registry methods that emit Tauri events into the webview**, where the JS pipeline runs them (apps/vizij-standalone/src-tauri/src/lib.rs:323-414; App.tsx:507-535). They are not device methods and are not on the ROS 2 plane (src-tauri/Cargo.toml features comment).
12. **The standalone also mounts the native `say` provider but connects it to nothing.** `vizij_arora_tts::host_module()` is on the arora (lib.rs:662), pinned to crates.io 1.0.0 (src-tauri/Cargo.lock:8455-8456), whose `say` streams raw Polly codes and states that mapping them is the caller's job (registry `vizij-arora-tts-1.0.0/src/lib.rs` header). The interpreter registers only the `look_at` fragment (src-tauri/src/skills.rs:23-30); `say_fragment`, `play_viseme`, `SAY_ID` do not occur in `src-tauri/src`. A `say` there plays audio through rodio on the Tauri host and its viseme stream moves no mouth. README.md:365-371 still says the module is "not yet wired into the standalone"; VIZ-126 (Backlog) is the ticket for wiring the players.
13. **The native device registers the whole speech surface.** `crates/vizij/src/device.rs:368-400` routes `SAY_ID` to the build's provider module, registers the `look_at`, `play_viseme` and `say` fragments with the face's rig prefix (honoring a bundle-embedded `skill::<id>` override), and mounts the gaze, viseme and TTS host modules. One provider per build: the cloud module by default, Piper under `tts-piper` (Cargo.toml features; tts_piper.rs).
14. **The `say` contract is a poll-on-tick function with a mutable `viseme` out-parameter.** `say(text, voice) -> Status`, ids in vizij-rs/crates/interop/vizij-arora-host/src/skills.rs:85-88, signature in crates/interop/vizij-arora-behavior/src/speech.rs:33-61. The cloud provider (crates/interop/vizij-arora-tts/src/lib.rs) spawns synthesis + playback on a tokio task, polls the `JoinHandle` with a no-op waker each tick and returns `Running` plus the current shape in `mutated` (139-177, 292-300); runs are keyed by `hash(text, voice)` because the module ABI carries no run id (313-322).
15. **The native playhead is a wall clock started at `sink.append`, sampled every 15 ms** (vizij-arora-tts/src/lib.rs:228-240; tts_piper.rs:194-206); rodio 0.20.1 exposes `Sink::get_pos()` (registry `rodio-0.20.1/src/sink.rs:351`), which the providers do not use.
16. **The provider stack is native-only: reqwest 0.13 (json), rodio 0.20 (`OutputStream::try_default`, `Sink`, `Decoder` over mp3), tokio `rt-multi-thread` + `time`, `std::env::var("API_URL")`, `std::thread::sleep`** (vizij-arora-tts/Cargo.toml; src/lib.rs:187, 206-245, 254-280). Verified: `cargo check --locked -p vizij-arora-tts --target wasm32-unknown-unknown` fails at tokio's `compile_error!("Only features sync,macros,io-util,rt,time are supported on wasm.")`. rodio's only wasm route is cpal's `wasm-bindgen` feature (`rodio-0.20.1/Cargo.toml:215`), and the blocking `play` loop cannot run on a single-threaded wasm target regardless.
17. **The say fragment turns the stream into standard viseme weights.** The fragment hosts the provider call in a `taskrun` node and feeds its first `mutated` slot to the shared lipsync driver at full weight (vizij-arora-host/src/skills.rs:480-508); the driver writes `standard/vizij/viseme/<shape>` for the 15 shapes with a 30 ms half-life crossfade read back from the store, the state `standard/vizij/viseme`, and `task/feedback` `{viseme, intensity}` (287-391). `play_viseme(shape, weight)` runs the same driver through an 80/250/150 ms envelope and is exclusive (430-469; vizij-arora-behavior/src/viseme.rs:35-43). The face's bundle maps standard weights onto its poses (device.rs:1419-1426: `play_viseme("aa")` reaches Quori's `pose_a`).
18. **Gaze is the `look_at(policy, target, frame)` skill writing the ROS4HRI gaze keys, which the profile maps to the standard eye controls** (skills.rs:138-275; crates/vizij/src/gaze.rs). Expressions are `standard/vizij/expression/<name>` over ROS4HRI's 25 names (face-standard.md:47-60). Neither the standalone nor the web writes those expression keys: the standalone writes its bundle's emotion group, the tutorial its emotion poses.
19. **The browser device (`vizij-arora-web`) registers no host module and no task fragment.** Its builder is RigHal + BlackboardStore + the graph interpreter + optional wasm guest modules (vizij-rs/crates/interop/vizij-arora-web/src/lib.rs:108-117); `say`, `viseme`, `gaze`, `look_at` do not occur in the crate. It exposes `skills()`/`skillSource(id)`, `profiles()`/`profile()`, `mappings()`/`mapping()` as JSON for the authoring app (lib.rs:376-456; npm/@vizij/runtime/src/index.ts:499-513) — the fragments as embeddable data, not registered players.
20. **arora's portable slice supports Rust host modules**, so a wasm `say` provider can be a `HostModule` rather than a wasm guest: the standalone builds `arora = { version = "9.11.1", default-features = false }` and calls `.with_host_module(vizij_arora_tts::host_module())` (src-tauri/Cargo.toml; lib.rs:661-662).
21. **tutorial-agent-face is already the "agent in JS drives the in-page face" shape, on three.js.** Gemini Live (`@google/genai`, `responseModalities: [AUDIO]`, key `VITE_GEMINI_API_KEY` at build) (vizij-web/apps/tutorial-agent-face/src/hooks/useGeminiLive.ts:123-176); mic via `getUserMedia` + `ScriptProcessor(4096)` → PCM16 → `session.sendRealtimeInput` (src/utils/audioManager.ts:85-137; useGeminiLive.ts:150-162); model audio scheduled as `AudioBufferSourceNode`s on a Web Audio `AudioContext`, playhead = `outputContext.currentTime - activeChainStartTime` (audioManager.ts:186-204, 372-386); lips from a phoneme aligner over the audio + transcript (src/hooks/useVisemeMouth.ts:75-142) on `rig/<faceId>/poses/<id>.weight` via `buildSemanticPoseWeightPathMap(…, "viseme")` (50-62, 144-157); the state topics on `rig/<faceId>/speech/{speaking,user_speaking,thinking}` (src/hooks/useSpeechGraphTopics.ts:21-58; src/utils/speechRuntime.ts:3-7); tools `set_gaze` → the standard eye controls resolved by `resolveFaceControls` (`/standard/vizij/left_eye/pos/x`, …) and `express_emotion` → emotion pose weights (src/hooks/useAgentFaceTools.ts:59-137, 263-332, 377-444; packages/@vizij/runtime-react/src/utils/faceControls.ts:53-58). Face: `VizijRuntimeFace` (three.js) over `Quori_Current_Extended.glb` (src/FaceApp.tsx:30-39, 325).
22. **vizij-showcase's voice section is a private copy of the Polly cursor**, `<audio>` + rAF, `buildSemanticPoseWeightPathMap(…, "viseme")`, with a text overlay (apps/vizij-showcase/src/components/VoicePanel.tsx:1-11, 34-52, 259-273; SpeechOverlay.tsx).
23. **semio_studio's `apps/vizij-app` has no speech surface**: `speech|say|viseme|tts|deepgram|openai` do not occur under `apps/vizij-app/src` or `src-tauri/src`.
24. **The player crate chain is on main but unpublished.** crates.io: vizij-arora-tts 1.0.0, vizij-arora-behavior 1.0.0, vizij-arora-host 1.0.0, vizij-api-core 1.0.0, vizij-graph-core 1.3.0 (`cargo search`); main: 2.0.0, 1.1.0, 2.1.0, 1.1.0, 1.4.0 (each crate's Cargo.toml). The standalone builds from crates.io (its Cargo.lock pins 1.0.0), so VIZ-126's prerequisite stands.

## Questions answered

**Q1 — `@vizij/speech-react` inventory, keys, consumers.** Hooks: `useSpeechRecognition` (Deepgram nova-3 streaming, VAD, auto-stop), `useConversation` (OpenAI chat completions, gpt-4o-mini), `useSpeechPlayback` (Polly speech marks → pose weights, `<audio>` clock). Services: `fetchVisemeData` → `POST {apiBase}/tts/get-visemes` and `/tts/get-audio` with `{voice, text}`; Deepgram/OpenAI key helpers over `VITE_*` env then localStorage. Consumers: the standalone only (findings 1-7); authoring and showcase keep their own copies (finding 2).

**Q2 — The standalone's controller, and whose job each piece is.** Modes `echo`/`conversation`; `speechConfig` fields as in finding 9; inputs `rig/<faceId>/speech/{speaking,user_speaking,thinking}`, emotion `rig/<faceId>/speech/emotion/<pose>`, viseme group by id or by "viseme" in the group name; visemes written straight to `rig/<faceId>/poses/<poseId>.weight` from JS (findings 6, 8-10; VIZ-126 states the same). Under "the face app hosts no conversation":
- *Agent's job:* microphone, Deepgram, OpenAI, the system prompt and agent name, the echo/conversation policy, choosing an emotion, deciding when the user is speaking or the agent is thinking, and the API keys. Every one of these is JS today and moves to the agent unchanged.
- *Face's (device's) job:* `say(text, voice)` with its audio playback and viseme stream, the lipsync driver (`standard/vizij/viseme/*`), the `speaking` state (derivable from a say run's status), the gaze skill, expressions on the standard keys. `user_speaking` and `thinking` are agent facts the agent writes onto the device's keys; they stay outside the face standard unless the standard grows a "conversation state" tier.
- *Neither's, retired:* the `speechConfig` fields that configure STT/LLM (`mode`, `agentName`, `systemPrompt`, `autoActivateMic`, `apiBaseUrl` for the JS pipeline) — they configure the conversation the face no longer hosts. `voice`, `visemeGroupId` and `emotionGroupId` describe the face and can remain bundle metadata (the viseme group is superseded by the standard adaptation; the emotion group by standard expressions once faces carry them).

**Q3 — tutorial-agent-face.** Gemini Live with audio in and out, `ScriptProcessor` mic capture, Web Audio playback, a phoneme aligner for lips, tool calls `set_gaze`/`express_emotion`, state topics on `rig/<faceId>/speech/*` (finding 21). It is the target demo's shape already — an agent in the page driving the in-page face through the runtime's inputs — with two differences: the face is three.js through `@vizij/runtime-react`, and the lips are the agent's own aligner over Gemini's audio rather than the device's `say` (Gemini Live returns audio, not text, so there is no text to hand to `say`).

**Q4 — The native device's speech surface; the browser device.** `say` = cloud provider over reqwest + rodio, poll-on-tick, viseme out-parameter (findings 14-16); Piper is the local sibling under `tts-piper` (finding 13). `play_viseme` and `say` share the lipsync driver over the standard viseme surface (finding 17); `look_at` is the gaze skill (finding 18). The browser device registers none of `say`, `play_viseme`, `look_at`, nor any host module; it serves the fragments as data only (finding 19). The standalone mounts the 1.0.0 `say` provider without the fragment, so its visemes reach nothing (finding 12).

**Q5 — Pieces for the target demo.** See the table under Evidence. The audio playhead clock belongs to the page's Web Audio `AudioContext` (`currentTime` of the output context), the only clock that tracks what the listener hears; the wasm `say` provider must sample its viseme timeline against that clock, never against a wasm-side wall clock (finding 15 is the native version of the same rule).

**Q6 — Fate of `@vizij/speech-react` and the speech CLI flags.** Retire the package: its playback half (`useSpeechPlayback`, `fetchVisemeData`, the Polly map, the pose-path helpers) is the face's job and is superseded by the device's `say` skill; its STT/LLM half (`useSpeechRecognition`, `useConversation`, key helpers) is agent glue with one consumer, better kept as source in the demo app than as a published package (no other app imports it; authoring has its own copy). The CLI flags `--deepgram-key`, `--openai-key`, `--auto-mic`, `--speech-mode`, `--silence-ms` configure a conversation the face app no longer hosts and have no native equivalent to inherit: they go with the standalone. `--api-url` survives as the `say` provider's `API_URL` (already read by the provider, finding 16), and `voice` as a `say` argument.

## Implications for the target picture

- **The device keeps `say` and the players; the agent keeps everything that listens or thinks.** The split already exists in code: the native device has the whole face side and none of the agent side; the web has the agent side and its own face side. The target removes the web's face side (JS lipsync on pose weights) and leaves its agent side in place.
- **A browser `say` is a port of the provider's I/O, not of its contract.** The contract, the fragment and the driver are target-independent data and pure Rust; only synthesis transport (reqwest → fetch, already there), playback (rodio → Web Audio) and the clock change. A wasm build of the provider is a new crate or a target-gated module, not a rewrite of the skill.
- **The playhead clock is the audio output's clock on every platform.** In the browser that is `AudioContext.currentTime`; the native providers should read `Sink::get_pos()` rather than `Instant::now()` for the same reason. Visemes sampled against any other clock drift with buffering.
- **Two viseme vocabularies collapse to one.** The web's pose-id map (Polly → `p, t_2, pose_pzzzfnvy, …`) disappears with the JS lipsync; every face is driven through the standard's 15 shapes and its own adaptation, the mechanism VIZ-126 asks for.
- **`user_speaking`, `thinking` and the emotion group are agent facts written onto face-specific inputs.** They survive as key writes from the agent, but they are outside the face standard: either the standard gains a conversation-state tier and an expression producer, or these remain per-face graph inputs the demo app knows by name.
- **tutorial-agent-face is the closest ancestor of the demo, not the standalone.** Its Gemini path returns audio rather than text, so its lips come from an aligner; a text-returning agent (OpenAI path) is the one that hands text to `say`. The demo needs one of the two, and only the text path exercises the device's `say`.
- **The `speak`/`interrupt`/`mute_microphone` WS methods disappear with the webview pipeline.** `say` is a described device method already (spawned as a task run, halted through its handle); interruption is the run's halt; a microphone is not the face's.

## Open questions

- **Where does Web Audio playback live: inside the wasm provider (web-sys) or in a JS callback?** Inside wasm keeps the provider self-contained but needs `wasm-bindgen-futures` for `decodeAudioData` and a way to unlock the `AudioContext` on a user gesture; a JS callback keeps wasm free of audio APIs but makes the provider depend on the page. Neither exists.
- **Does the say fragment's `taskrun` node run on the browser device's interpreter unchanged?** The fragment tests run on the native interpreter (test results below); `vizij-arora-web` uses the same `ProcessingGraph` type but has never registered a task fragment, so the wasm-side interpreter module path (SPAWN/HALT through `arora-behavior`'s interpreter module) is unverified in the browser.
- **Should the standard gain conversation-state keys (`speaking`, `user_speaking`, `thinking`) and an expression producer?** Today they are per-bundle graph inputs; an agent that targets any face needs standard names.
- **Which agent does the demo ship — Gemini Live (audio in/out, tutorial) or Deepgram + OpenAI (text, standalone)?** Only the text path drives the device's `say`; the Gemini path would need `play_viseme` fed by an aligner in JS, which keeps a JS lipsync producer alive.
- **What does `say` do when the same `(text, voice)` is spoken twice concurrently?** Runs are content-keyed (finding 14); the ABI's missing run id is an arora-sdk question, not a browser one, but it surfaces as soon as an agent repeats itself.
