## Summary

The import/export pipeline aims to restore authoring state using only Vizij GLB files and rig graph JSON. The end state removes dependency on legacy summary artifacts while maintaining lossless round-trips.

## Current Behaviour *(As of Today)*

- GLB imports provide robot hierarchy, baked defaults, and feature label overrides.
- Rig graph exports include node graphs generated by `buildRigGraphSpec`.
- Summary artifact still required to fully hydrate authoring state (bindings, expressions, selection state).

## Target Workflow

1. **Load & Normalise GLB** – Import robot hierarchy, baked defaults, feature overrides, and immediately run the identifier normaliser so later comparisons operate on canonical IDs.
2. **Parse Rig Graph** – Traverse the imported GraphSpec to reconstruct standard inputs, bindings, slot remaps, expression trees, and metadata describing their source nodes.
3. **Hydrate Authoring Store** – Seed controller state (`bindings`, `inputBindings`, `standardInputs`, `inputValues`, selections) and rerun catalogue/auto-input builders to repopulate derived metadata.
4. **Discrepancy Review Wizard** – Present the reconciled IR vs. source graph deltas in a dedicated wizard (instead of blocking popups) so authors can accept, remap, or ignore discrepancies with full context.
5. **Pose Rig Remapping (Optional)** – When a pose rig is included, map its pose outputs to the main rig’s inputs with an interactive remapping table before the import finalises.
6. **Validation & Commit** – Rebuild a GraphSpec from the hydrated store, run structural diffing against the imported graph/pose rig, and require authors to acknowledge remaining warnings prior to editing.
7. **Export Loop** – Persist the reconciled state (including discrepancy decisions and pose remaps) so future exports/imports stay lossless without replaying the wizard unnecessarily.

## Discrepancy Resolution Workflow

### Trigger & Entry

- Runs automatically after GLB + graph parsing succeeds and before changes touch the live authoring store.
- Replaces modal popups with a multi-step wizard or docked drawer that summarises issues by category (Identifiers, Missing Nodes, Value Drift, Expression Mismatch).

### Data Sources

- **GLB Snapshot** – Canonical robot hierarchy and baked defaults post-normalisation.
- **GraphSpec Input** – Imported rig graph prior to hydration.
- **Hydrated IR** – Rebuilt authoring store projected back into GraphSpec form for comparison.

### Review Surfaces & Actions

1. **Identifier Drift Panel**
   - Shows rows where node/input IDs differ between GLB and graph.
   - Actions: `Accept Proposed ID`, `Rename Imported Node`, `Create Alias`. Accept/rename updates the reconciliation map persisted in the project metadata.
2. **Missing/Extra Elements Panel**
   - Lists nodes or bindings that exist only on one side.
   - Actions: `Create Placeholder`, `Remap to Existing`, `Mark Intentional`. Creating placeholders hydrates stubs that authors can flesh out later.
3. **Expression/Value Mismatch Panel**
   - Displays reconstructed infix expressions next to imported compute subgraphs with diff highlights.
   - Actions: `Adopt Imported Graph`, `Adopt Rebuilt Expression`, or launch the expression editor for manual tweaks.
4. **Slot Remap Conflicts**
   - Visualises slot aliases where regenerated identifiers no longer match.
   - Actions: drag-to-remap UI plus a `Bulk Apply Suggestion` that leverages heuristics (prefix/suffix matching, semantic tags).

Each action writes to a `reconciliationLog` stored alongside the project so subsequent imports can auto-apply prior decisions or at least pre-fill defaults.

### Persistence & Re-run Rules

- The wizard persists its completion state; authors can opt to re-open it later from the import history panel.
- If new discrepancies appear (e.g., GLB update), only the affected rows reopen, preventing full re-review.
- All accepted changes update the hydrated IR immediately, then the validation diff re-runs before allowing the import to finish.

## Pose Rig Import & Remapping Workflow

### Manifest & Detection

- Pose rig bundles ship with `pose-rig.json` (GraphSpec/IR snippet) plus a manifest describing:
  - Pose set metadata (name, tags, author, schema version).
  - Required standard inputs + expected ranges per pose output.
  - Optional compatibility hints (e.g., `hand.L/wrist.rotate` → `arm.L/wrist.rotate`).
- When the import detects a pose rig file, it inserts a “Pose Mapping” step after the discrepancy wizard.

### Remapping Table

- Left column: pose rig outputs grouped by pose.
- Middle column: auto-suggested main rig targets (based on canonical IDs, tags, anatomical categories).
- Right column: resolution controls (`Auto`, `Manual`, `Skip`).
- Inline validation chips show readiness (`Ready`, `Needs Scaling`, `Missing Target`).

### Workflow Steps

1. **Auto Match** – System pre-selects matches with ≥90% confidence using identifier and semantic tag similarity.
2. **Manual Override** – Authors can search main rig inputs, drag-and-drop matches, or type custom expressions.
3. **Normalization Helpers** – Provide value range previews and scaling presets (e.g., convert degrees ↔ radians) before committing the mapping.
4. **Batch Ops** – Select multiple poses/outputs to apply the same mapping or scaling.
5. **Validation** – Run a mini diff ensuring mapped targets exist and produce compatible types; unresolved rows block completion with actionable messaging rather than popups.

### Persistence & Export

- Successful mappings update both the pose library and the main rig bindings so poses can be edited immediately.
- The mapping table writes to the pose rig manifest for future reuse; exports include the resolved target IDs and any scaling metadata.
- When re-importing an updated pose rig, previous mappings auto-populate but highlight conflicts if upstream poses changed.

## Key Considerations

- **Identifier Normalisation**: Must happen consistently at creation/import time to avoid mismatches.
- **Expression Reconstruction**: Canonical infix representation with regenerated aliases to maintain readability.
- **Validation**: Structural diffing rather than strict textual comparison to avoid noise.
- **User Feedback**: When mismatches occur, present actionable remediation steps.

## Usage Notes *(Pending Implementation)*

- **Import-Only Workflow**:
    1.  **Load Asset**: Drag and drop a GLB file or use the "Import" button.
    2.  **Review Alerts**: The system checks for ID mismatches and missing nodes.
    3.  **Accept IDs**: If prompted, accept the proposed ID normalizations to ensure compatibility with the current system. These decisions are persisted for future imports.
    4.  **Verify State**: Check the "Drivers" panel to ensure all inputs and bindings are correctly hydrated.
    5.  **Export**: Use the "Export" button to save the reconciled state.
- **Troubleshooting**:
    - **ID Mismatches**: If you see repeated ID mismatch warnings, ensure you have accepted the proposed changes in the import wizard.
    - **Missing Nodes**: If nodes are missing, check if the source GLB has changed. You may need to re-import the original GLB or update the graph to match the new hierarchy.
    - **Logs**: Check the browser console for detailed import logs, including specific node IDs and binding errors.
